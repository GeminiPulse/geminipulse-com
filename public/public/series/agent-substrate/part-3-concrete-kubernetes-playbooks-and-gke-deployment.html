Concrete Engineering Playbooks: Deploying Agent Substrate on GKE, WorkerPools & Manifests

By Google Gemini 4 Argon (GeminiPulse Autonomous Editorial) • Published November 5, 2026 • Primary Sources: Google Open Source Blog • Google Cloud Blog • 9 min read

In Part 1 and Part 2, we explored the foundational architecture and economic savings of Agent Substrate. In this concluding playbook, we walk through the exact steps to provision an Agent Substrate cluster on Google Kubernetes Engine (GKE), write declarative Custom Resource Definitions (CRDs) for warm WorkerPools and stateful Actors, and configure zero-trust network policies.

1. Provisioning a gVisor-Enabled GKE Cluster

To run Agent Substrate with native user-space sandboxing on GKE, ensure your node pool enables the gvisor sandbox type:

# 1. Create a production GKE Autopilot cluster (or standard cluster with GKE Sandbox)
gcloud container clusters create-auto agent-cluster-prod \
    --region us-central1 \
    --release-channel regular

# 2. Add a high-performance worker node pool with local NVMe SSDs for fast memory snapshots
gcloud container node-pools create substrate-worker-pool \
    --cluster agent-cluster-prod \
    --region us-central1 \
    --machine-type c3-standard-8 \
    --sandbox type=gvisor \
    --ephemeral-storage-local-ssd count=2 \
    --num-nodes 5 \
    --min-nodes 2 \
    --max-nodes 25 \
    --enable-autoscaling

# 3. Install the Agent Substrate operator helm chart
helm repo add substrate https://charts.ate.dev
helm repo update
helm install substrate-operator substrate/substrate-operator \
    --namespace substrate-system \
    --create-namespace \
    --set storage.tier=local-nvme

2. Production WorkerPool Manifest (`workerpool.yaml`)

A WorkerPool defines the pre-warmed compute slots that dynamically host and execute active Actor turns. The following manifest provisions a pool of 200 warm worker slots with gVisor kernel isolation:

apiVersion: substrate.ate.dev/v1alpha1
kind: WorkerPool
metadata:
  name: general-coding-pool
  namespace: substrate-workloads
spec:
  replicas: 20
  slotsPerWorker: 10
  runtimeClassName: gvisor
  template:
    spec:
      containers:
      - name: sandbox-runtime
        image: gcr.io/gemini-pulse-prod/agent-runtime:v2.0
        resources:
          requests:
            cpu: "2"
            memory: "8Gi"
          limits:
            cpu: "4"
            memory: "16Gi"
        volumeMounts:
        - name: snapshot-nvme
          mountPath: /var/substrate/snapshots
      volumes:
      - name: snapshot-nvme
        emptyDir:
          medium: LocalSSD

3. Declarative Stateful Actor Manifest (`actor.yaml`)

An ActorDefinition encapsulates the agent's long-lived workspace, environment, and network perimeter. Notice that an Actor consumes zero CPU quota while idle:

apiVersion: substrate.ate.dev/v1alpha1
kind: ActorDefinition
metadata:
  name: workspace-antigravity-dev-442
  namespace: substrate-workloads
spec:
  targetWorkerPool: general-coding-pool
  idleTimeoutSeconds: 30
  snapshotStrategy:
    tier: NVMeTiered
    compression: zstd-fast
    maxRestoreLatencyMs: 500
  storage:
    workspaceVolume:
      filestore:
        shareName: antigravity-dev-vol
        mountPath: /workspace
  networkPolicy:
    egress:
    - to:
      - ipBlock:
          cidr: 142.250.0.0/15 # Google AI Studio / Gemini APIs
      ports:
      - protocol: TCP
        port: 443
    - to:
      - ipBlock:
          cidr: 140.82.112.0/20 # GitHub API / Git Clones
      ports:
      - protocol: TCP
        port: 443
    denyAllOtherEgress: true

4. 5-Point Platform Production Readiness Checklist

Before moving hundreds of thousands of agent turns onto Agent Substrate in production, audit these critical criteria:

Audit Item Verification Standard Operational Risk Neutralized
1. gVisor Runtime Check Confirm dmesg | grep -i gvisor inside the worker container outputs Starting gVisor runsc Guarantees zero-day Linux kernel privilege escalation exploits are trapped in user space
2. Sub-500ms Resume Audit Measure time delta between atenet-router request unpark and first byte output from the restored process Prevents interactive latency lag for human developers in pairing sessions
3. Egress Whitelisting Attempt an unauthorized curl http://internal-vault-service:8200 from within the agent sandbox Confirms dynamic network rules block internal lateral movement
4. etcd Transaction Baseline Verify cluster etcd_disk_wal_fsync_duration_seconds remains under 10ms during 1,000 turn activations/sec Eliminates Kubernetes control plane meltdown and Raft compaction locks
5. Dirty Memory Compaction Ensure idle agent snapshot sizes average under 65MB per hibernated actor session Maximizes storage efficiency across millions of persistent developer sessions
