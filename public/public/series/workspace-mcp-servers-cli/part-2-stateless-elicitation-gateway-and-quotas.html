1. How Stateless Form Elicitation Works on /mcp/v1

Google Workspace MCP servers implement the stateless 2026-07-28 MCP Elicitation specification. Because policy checks happen server-side on every single invocation, an agent host cannot hardcode which tools need confirmation or cache approval state locally.

  1. Initial Call: The MCP host calls /mcp/v1 with tools/call and declares elicitation capability in params._meta. (Prebuilt hosts like Google Antigravity or Claude Desktop should set local tool confirmation to Always allow so users are not prompted twice.)
  2. InputRequiredResult Pause: When external sharing, trashing, or admin rules trigger confirmation, the server pauses and returns resultType: "input_required", an inputRequests["approval_choice"] form object (mode: "form"), and an opaque requestState token bound strictly to the exact tool arguments.
  3. Argument-Locked Retry: After the user picks an option (for example ALLOW_ONCE or DENY_ONCE; moving files to Trash never grants persistent approval and permanent deletion is blocked for third-party agents), the host replays the exact same tool name and arguments with top-level params.requestState and params.inputResponses.
  4. /mcp/v1self Fallback: Hosts that do not yet implement form elicitation can point to /mcp/v1self, which hides tools that always require default approval (while still enforcing policy-triggered checks on sensitive resources).

3. Cloud Agent Gateway Enforcement

Inside Google Cloud, Agent Gateway terminates client-to-agent and agent-to-MCP traffic. Every registered agent gets a cryptographic SPIFFE Agent Identity in Agent Registry authenticated via mTLS and DPoP, gated by default-deny IAM Unified Access Policies, scanned inline by Model Armor and Semantic Governance Policies, and exported to Security Command Center, Cloud Audit Logs, and Wiz.
