Why Code Review—Not Code Generation—Is the Real Bottleneck

What 241,000 live Linux kernel reviews taught Google AI & Infrastructure about turning skeptical maintainers into daily users.

Every engineering team shipping with coding agents hits the same wall: generating diffs became cheap, while proving those diffs safe remained painfully expensive. Across the Linux kernel—more than 35 million lines of code and 85,000+ annual commits—maintainers were facing rising queues of plausible-looking AI patches and low-signal security reports. On November 19, 2026, Google’s Roman Gushchin and VP/Google Fellow Eric Brewer <a href="https://cloud.google.com/blog/products/application-development/lessons-from-building-sashiko-an-agentic-code-review-system" target="_blank" rel="noopener">published seven months of hard production data</a> from Sashiko, the open-source Gemini review system Google donated to the Linux Foundation and runs free at sashiko.dev.

Rather than judging Sashiko on synthetic coding puzzles, Google measured whether real kernel maintainers trusted its mailings. More than 75 subsystem lists opted in, over 1,500 kernel developers replied directly to reports on the mailing lists, and LWN.net named Sashiko the top bug reporter of the Linux 7.2 release cycle. Even Linus Torvalds weighed in on lore.kernel.org, noting that Sashiko surfaces deep, subtle findings where "the AI is 100% correct" and acts as an engine of patch trust.

The mainline outcome numbers explain why skeptics converted. Across the 18 kernel releases before Sashiko (Linux 6.2 through 6.19, covering 254,000 commits), an average of 3.4% of merged commits required a follow-up fix within 60 days. After Sashiko rolled out, that 60-day fix rate fell to 2.8% in Linux 7.1 and 2.2% in Linux 7.2—a 35% reduction—while the 30-day fix rate dropped from 2.3% to 1.4%. Across 21,500 tracked mainline commits, patches with a clean Sashiko pass needed a 60-day fix just 0.9% of the time versus 7.6% when merged over a critical warning (an 8x raw risk gap, or 6.3x adjusted for patch size).

Crucially, Sashiko did not hide behind closed prompts or per-developer API paywalls. Google runs sashiko.dev at zero cost to kernel contributors with every prompt, git tool call, reasoning step, and ruled-out candidate published in the open—even running "Sashiko for Sashiko" to audit its own repository and prompt pipeline before human review.

“Coding agents are not great at reviewing their own code. Creating a functional solution is often just 5–10% of the work; proving it safe across every unseen caller requires an independent verification loop.”

CHAPTER 02 / 04 · WHAT THIS MEANS FOR YOU ADAPTIVE READER QUESTIONS
FOR ENGINEERING LEADERS

Why did Google pair Sashiko with a separate benchmark of ~1,000 missed kernel bugs?

Gushchin and Brewer note that intuitive prompt tweaks frequently backfired in production. Evaluating every pipeline change against ~1,000 real historical bugs that slipped past human kernel experts proved that Gemini 4 Carbon (high) reaches 75.8% recall while keeping false alarms low enough for 75+ maintainer lists to opt in.

FOR CODING AGENT TEAMS

Can the same Gemini model that wrote a feature also review its own pull request?

Google warns against it: models optimize to ship working patches within a token budget and share their own blind spots. Even running an independent Sashiko pass with external domain guides and symmetrical proof rules catches cross-file regressions that the authoring pass missed.

FOR OPEN-SOURCE & ENTERPRISE REPOS

Is Sashiko locked to C and the Linux kernel?

No. Its five-stage engine is language-agnostic and open source, relying on git inspection tools plus per-subsystem maintainer notes—making the same playbook directly applicable to GCC, LLVM, Git, or internal enterprise monorepos.

Separating Candidate Discovery From Symmetrical Proof

How Sashiko prevents token-stingy corner cutting and catches shaky self-dismissals across 100+ git tool calls.

Sashiko’s core insight is psychological as much as architectural: LLMs trained for concise responses tend to stop looking once they find one flaw, get swayed by persuasive commit messages, or prematurely dismiss a real bug by guessing that an unseen caller holds a lock. Sashiko neutralizes all three failure modes by decoupling candidate discovery from bug verification across five sequential stages.

Stage 1 (Gather Context & Plan) pulls modified functions, struct definitions, direct callers, and subsystem domain guides—then assigns specialist passes and reasoning budgets based on patch complexity. Stage 2 (Up to 7 Parallel Specialist Sessions) runs isolated single-focus passes—covering commit intent, implementation match, control flow, resource lifetimes, locking, security, and hardware—averaging roughly 100 git tool calls per review and emitting two mandatory lists: believed concerns and ruled-out candidates with supporting code.

Stage 3 (Triage) audits both lists together specifically to hunt shaky self-dismissals—cases where a specialist spotted a real hazard and talked itself out of reporting it without checking every caller. Stage 4 (Per-Bug Deep Checks) spawns an isolated verification agent per hard case under a strict symmetrical rule: neither a bug claim nor a dismissal is accepted without concrete git-verified proof across all call sites. Finally, Stage 5 formats concise maintainer-style review questions.

01 · Force Every Review Specialist to Log What It Dismissed
Requiring both concerns and dismissed_candidates lets an independent Triage model catch premature assumptions before silent bugs slip into production.
02 · Isolate One Concern Class per Parallel Session
Split locking, memory lifetimes, and security into separate calls (for example fast Hydrogen sweeps escalated to Carbon High triage) so one minor nit never crowds out a critical race condition.
03 · Apply the Symmetrical Proof Rule Across All Call Sites
Never accept "likely safe because caller validates" unless the verifier reads every caller via git search and cites the exact file and line.
SASHIKO-PATTERN TWO-STAGE REVIEW GATE (@google/genai v3.6.1) 
import { GoogleGenAI } from "@google/genai";

// Pattern inspired by Google's open-source Sashiko pipeline:
// 1) Parallel single-focus specialist discovery (concerns + ruled-out candidates)
// 2) Independent Gemini 4 Carbon (high) triage auditing shaky self-dismissals
const ai = new GoogleGenAI({});

const SPECIALIST_FOCUSES = [
  "commit_intent_and_contract",
  "resource_lifetimes_and_leaks",
  "locking_and_concurrency",
  "security_and_bounds",
];

export async function runSymmetricalCodeReview(diffWithCallers, maintainerNotes) {
  const specialistRuns = await Promise.all(
    SPECIALIST_FOCUSES.map((focus) =>
      ai.interactions.create({
        model: "gemini-4-hydrogen",
        input: JSON.stringify({
          focus,
          maintainerNotes,
          diffWithCallers,
          schema: "Return { concerns: [], dismissedCandidatesWithProof: [] }",
        }),
        generation_config: { thinking_level: "medium", max_output_tokens: 16384 },
      })
    )
  );

  // Stage 3 & 4: Symmetrical triage requires proof across ALL call sites
  const triageDecision = await ai.interactions.create({
    model: "gemini-4-carbon",
    input: JSON.stringify({
      rule: "Promote any shaky self-dismissal that lacks concrete caller proof.",
      specialistReports: specialistRuns.map((r, i) => ({
        focus: SPECIALIST_FOCUSES[i],
        report: r.output_text,
      })),
    }),
    generation_config: { thinking_level: "high", max_output_tokens: 32768 },
  });

  return triageDecision.output_text;
}
